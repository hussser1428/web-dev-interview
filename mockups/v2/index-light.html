GET đọc, POST tạo, PUT thay toàn bộ, PATCH sửa một phần, DELETE xoá. Safe = không đổi dữ liệu (GET, HEAD). Idempotent = gọi nhiều lần cho kết quả như một lần (GET, PUT, DELETE).
Vì sao quan trọng: client, proxy và retry logic dựa vào hai tính chất này. Request idempotent có thể tự động gửi lại khi timeout mà không sợ tạo bản ghi trùng; POST thì không.

export async function auth(req, res, next) {
  const token = req.headers.authorization?.slice(7);
  const p = jwt.verify(token, SECRET);
  // cache version 60s để không query DB mỗi request
  let v = await redis.get(`tv:${p.sub}`);
  if (v === null) {
    v = (await db.user.find(p.sub)).tokenVersion;
    await redis.set(`tv:${p.sub}`, v, { EX: 60 });
  }
  if (Number(v) !== p.tv) return res.sendStatus(401);
  req.user = p;
  next();
}

Index trong database hoạt động thế nào? Khi nào index làm chậm hệ thống?

Nhận xét

Giải thích được index giúp tìm nhanh hơn nhưng chưa nói tới cấu trúc B-tree, chưa nêu chi phí khi INSERT/UPDATE và trường hợp index không được dùng (hàm trên cột, LIKE '%x').

Câu trả lời tốt hơn

Index thường là B-tree sắp xếp theo cột, giúp tìm kiếm O(log n) thay vì quét toàn bảng. Đổi lại mỗi lần ghi phải cập nhật index nên bảng ghi nhiều không nên index tràn lan. Composite index theo thứ tự cột hay lọc nhất; kiểm tra bằng EXPLAIN.

Vì sao shop-api lưu giỏ hàng trong Redis mà không dùng PostgreSQL? Redis restart thì sao?

Bạn đã trả lời

Vì Redis nhanh hơn, giỏ hàng đọc nhiều. Nếu Redis restart thì… chắc người dùng phải thêm lại giỏ hàng ạ.

Nhận xét

Đúng ý "đọc nhiều, cần nhanh" nhưng dừng ở đó. Chưa nói Redis có persistence (RDB/AOF), chưa cân nhắc giỏ hàng là dữ liệu người dùng quan tâm, và chấp nhận mất dữ liệu mà không đưa ra phương án.

Câu trả lời tốt nên có

Giỏ hàng thay đổi liên tục và cần đọc nhanh nên để ở Redis (hash theo user, TTL 30 ngày). Bật AOF everysec để restart chỉ mất tối đa ~1 giây. Khi checkout thì ghi đơn vào PostgreSQL trong transaction — dữ liệu quan trọng luôn nằm ở DB, Redis chỉ là trạng thái tạm.

Lần sau nên
Trả lời theo khung: lý do chọn → rủi ro → cách giảm rủi ro. Người phỏng vấn product hỏi "restart thì sao" là đang chờ bạn nói về đánh đổi.

Ví dụ thực tế
Giống chuông báo cháy cứ kêu mỗi lần nấu ăn có khói: vài lần sau mọi người tắt chuông hoặc lờ đi — tới khi cháy thật thì không ai chạy. Ca trực nhận 50 alert mỗi đêm, 48 cái tự hết sau 2 phút, nên người trực quen tay bỏ qua — và bỏ qua luôn alert thật lúc hệ thống sập.
• Cảnh báo theo triệu chứng thay vì nguyên nhân: tỉ lệ lỗi tăng, latency vượt SLO, thay vì CPU 80%. CPU cao mà người dùng không bị ảnh hưởng thì không cần đánh thức ai lúc 3 giờ sáng.
• Phân mức: page (cần xử lý ngay) và ticket (xử lý trong giờ làm việc).
• Dùng điều kiện for (ví dụ kéo dài 5 phút) để tránh nhiễu do spike ngắn; với SLO, dùng burn-rate alert nhiều cửa sổ thời gian.
• Mỗi alert có owner, runbook link, dashboard liên quan và mô tả ảnh hưởng.

SLO

Service Level Objective · mục tiêu mức dịch vụ
Mục tiêu chất lượng dịch vụ mà team tự đặt ra và đo bằng con số trong một khoảng thời gian. Ví dụ: 99,9% request trả lời dưới 300 ms trong 30 ngày. Nằm giữa SLI (con số đo được thực tế) và SLA (cam kết với khách hàng, thường thấp hơn SLO để còn khoảng an toàn).
Đời thường
Một quán cà phê tự đặt mục tiêu "95% đơn giao trong 10 phút". Đó là SLO. Con số thực tế tuần này 93% là SLI. Còn "trễ quá 20 phút thì miễn phí" in trên menu là SLA.
